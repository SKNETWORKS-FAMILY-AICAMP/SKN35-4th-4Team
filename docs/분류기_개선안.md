# 분류기(classifier) 개선안과 근거

2026-11-04 · 작성: 채영 · 근거 데이터: `eval/results/` (코드 변환 평가 50문항, RAGAS 문서 질의응답 24문항)

## 한 줄 요약

지금 실제 사용자가 받는 답의 품질을 가장 많이 깎는 건 검색이 아니라 **분류기**다.
문서 질문 24개 중 **마이그레이션 질문인데도** search 가 아닌 경로로 간 것이 9개이고, 그중 general 로 간 8개의 정답 사실 일치는
**0.08** 로 시스템 프롬프트 없는 일반 LLM(0.17)보다도 낮다. 같은 질문을 search 로 보내면 **0.69** 가 나온다.

> **팀 결정 (2026-11-04)**: 이 챗봇은 마이그레이션에 집중하는 RAG 다. search 는 마이그레이션(버전 변경) 지식 질문에만 쓰고,
> 나머지는 LangChain 질문이어도 **모두 general** 로 고정한다. 아래 개선안은 이 범위를 바꾸지 않고, 범위 안의 질문을 제대로 보내는 데만 집중한다.

## 3. 고치는 방법

### 3-1. 코드로 확실한 것은 코드로 정한다 (LLM 앞단 규칙) — ④ ⑤ 해결

LLM 에 묻기 전에, 메시지에서 확인 가능한 사실로 먼저 결정한다.

```
옛 import 있음 = 메시지 속 import 문 중 하나라도 import 대응표(import_map)에 정확히 매칭 (lookup 재사용)
변환 의도 있음 = 바꿔|바뀌|고쳐|수정|변환|마이그레이션|올려|업그레이드|돌아가게|설치|에러|오류|Error|deprecated|어떻게 하죠 ...

1. 옛 import 있음 AND 변환 의도 있음  → migration (LLM 호출 없이 확정)
2. 코드 블록도 import 문도 없음        → migration 금지 (LLM 이 migration 이라고 해도 search 로)
3. 나머지                              → LLM 분류
```

- 근거: 1-3 의 6개는 모두 옛 import(대응표 정확 매칭, 코드로 확인함) + 변환 의도 → 규칙 1 로 migration. r03 은 코드 없음 → 규칙 2 로 search.
  (q06 "어디가 **바뀌**었는지", q09 "뭘 **설치**해야" 때문에 바뀌 · 설치 를 의도 단어에 넣었다.)
- 오분류 위험 확인: route_probes 의 general 질문 중 코드가 있는 p09 (`langchain_core.prompts` = 1.x 경로라 대응표 매칭 없음), p12 (`import os` 뿐, 지시문 주입) 는 규칙 1 에 걸리지 않는다.
- import 대응표 매칭은 검색기가 이미 쓰는 `lookup()` 을 그대로 쓴다 (새 데이터 없음).
- 한계: 버전을 내리는 질문(q31~q34, 1.x 코드 → 0.x)은 코드가 최신이라 옛 import 가 없어 규칙 1 에 걸리지 않는다 → 지금처럼 LLM 이 분류.
  지금 평가에서 이 질문들은 LLM 이 migration 으로 맞게 분류하고 있다.

### 3-2. 범위는 그대로, 범위 안의 질문을 제대로 보낸다 — ② ③ ①' 해결

팀 결정대로 **search = 마이그레이션(버전 변경) 지식 질문, 그 밖은 모두 general** 을 유지한다.
"LCEL이 뭐야?", "create_agent 사용법", "RAG 만드는 법", ChatOpenAI 옵션 질문(r24)은 계속 general.

(1) 코드 규칙 하나 추가 — 옛 API 이름이 나오면 general 금지 (③)

```
옛 API 이름 = 코드 블록을 뺀 질문 문장에 나온 이름 중, import 대응표에서 1.x 기준 langchain-classic 으로
              밀려난 이름(kind = classic_fallback, 499개: LLMChain · RetrievalQA · AgentExecutor ·
              ConversationBufferMemory · create_react_agent 등)
→ 옛 API 이름이 있으면 general 금지 (LLM 이 general 이라고 해도 search)
```

- 검색기에 이미 넣은 `lookup_names()` 를 그대로 쓴다.
- 코드로 확인한 결과: r01 · r02 · r04 · r05 · r14 (5개) 가 걸려 search 로 간다.
- 오분류 위험 확인: route_probes 의 general 질문 p06~p12 는 하나도 걸리지 않는다.
  r24 의 `ChatOpenAI` 는 1.x 에도 그대로 있는 이름(native)이라 걸리지 않는다 → 팀 결정대로 general 유지.

(2) 프롬프트 수정 (②, ①' — 코드 규칙으로 못 잡는 r08 · r09 · r11 용)

- 규칙 4 에 예외 추가: "옛 방식 **대신** 새 방식으로 어떻게 하는지 / 옛 코드를 **옮기면** 어떻게 되는지" 는 '사용법' 이 아니라 마이그레이션 질문 → search
- search 예시 추가: "LLMChain 대신 어떻게 만들어요?", "AgentExecutor를 LangGraph로 옮기면?", "LangChain 1.0은 파이썬 몇 버전부터?",
  "langchain-classic은 언제 설치해요?", "옛날 메모리 말고 LangGraph 메모리를 쓰면 뭐가 좋아요?"
- general 예시는 그대로 둔다 ("LCEL이 뭐야?", "create_agent 사용법", "RAG 파이프라인 만드는 법")

### 3-3. 안정성 — ⑥ ⑦ 해결

- `temperature=0.7` → `0`
- 출력 정리: `strip().strip('.\"\\'').lower()`, 세 값 밖이면 `general` (팀 범위: 확실한 것만 search · migration)

### 같이 고칠 평가 도구 문제
