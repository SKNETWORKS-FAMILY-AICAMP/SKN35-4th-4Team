# 2026-11-05 비밀번호 로그인 구현 과정과 점검

팀: SKN35 4Team  
기록 시점: 2026-11-05 오전  
기록 목적: 로그인에 비밀번호를 붙인 과정과, 전체 기능 점검에서 찾은 것 · 고친 것을 개인 작업 기록으로 남긴다.

> 백엔드는 ① 담당이다. 아래 비밀번호 로직은 ④가 화면(로그인 · 가입)을 고치면서 시험 삼아 1차로 연결해 본 것이고, ①이 전체를 검토해 `dev` 에 반영했다.

## 1. 왜 비밀번호를 붙였나

- 3차는 아이디만으로 로그인했다. 아이디를 아는 사람은 누구나 남의 대화 기록을 열 수 있었다.
- 4차는 웹으로 배포하므로 아이디 + 비밀번호로 바꿨다. 아이디 규칙(한글 · 영문 · 숫자 · _ 2~20자)은 3차와 같게 두었다.

## 2. 흐름

```text
[가입]                                         [로그인]
아이디 · 비밀번호 · 비밀번호 확인                 아이디 · 비밀번호
        │                                             │
입력 검사: 아이디 규칙 · 6~64자 · 확인 일치 · 중복     users 테이블에서 아이디 찾기
        │                                             │
make_password()                                check_password()
  무작위 소금 + pbkdf2_sha256 100만 번 반복         저장된 소금 · 반복 횟수로 다시 계산해 비교
        │                                             │
TiDB users.password 에 해시만 저장  ─────────▶   일치 → 세션 키 새로 발급 → 로그인
        │                                        틀림 · 없는 아이디 → 같은 안내 문구
세션 키 새로 발급 → 로그인
```

## 3. 만든 것

| 부분 | 내용 |
|---|---|
| 모델 | `users.User` 에 `password` 칸 (`CharField(128)`, `db_default=""`) |
| 마이그레이션 | `users/migrations/0002_user_password.py` → `ALTER TABLE users ADD COLUMN password varchar(128) DEFAULT '' NOT NULL` (TiDB 반영) |
| 가입 API | `POST /api/users/signup/` `{user_id, password, password_confirm}` → 검사 4가지 → `make_password()` 로 저장 → 세션 로그인 |
| 로그인 API | `POST /api/users/login/` `{user_id, password}` → `check_password()` 비교 → 세션 로그인 |
| 화면 | 로그인: 비밀번호 칸 / 가입: 비밀번호 · 비밀번호 확인 칸, 6자 미만 · 확인 불일치는 화면에서 먼저 막음 |

정한 것과 이유

| 결정 | 이유 |
|---|---|
| 원문이 아니라 **해시**로 저장 | 해시는 되돌릴 수 없어서 DB 가 새도 비밀번호 원문을 알 수 없음 |
| Django `make_password()` 그대로 사용 | 무작위 소금(사람마다 다름)과 100만 번 반복을 알아서 해 줌. 직접 만들지 않음 |
| `db_default=""` | 이 칸을 모르는 다른 브랜치 코드가 사용자를 넣어도 DB 가 빈 값으로 채워 오류가 안 남 |
| 틀린 비밀번호와 없는 아이디를 **같은 안내 문구**로 | 어느 쪽이 틀렸는지 알려 주면 남의 아이디가 있는지 떠볼 수 있음 |
| 로그인 · 가입 때 세션 키 새로 발급 (`cycle_key`) | 로그인 전 세션 번호를 그대로 쓰는 세션 고정 공격 방지 |
| 비밀번호 칸 전에 만든 아이디는 로그인 안 됨 | 비밀번호가 비어 있음 → "새 아이디를 만들어 주세요" |

## 4. 해시를 이해한 것

- 해시는 어떤 글자를 넣어도 정해진 길이의 알 수 없는 글자로 바꾸는 계산이다. 같은 입력이면 항상 같은 결과, 한 글자만 달라도 완전히 다른 결과, 결과로 원문을 되돌릴 수 없다.
- 그래서 서버는 원문을 몰라도 "입력한 값을 같은 방식으로 계산한 결과가 저장된 값과 같은지"만 보면 된다.
- 소금: 같은 비밀번호라도 사람마다 해시가 달라져서, 흔한 비밀번호의 해시를 미리 계산해 둔 표로 한꺼번에 푸는 공격을 막는다. 같은 `abc12345` 를 두 번 해시하면 결과가 달랐다.
- 100만 번 반복: 로그인 한 번은 1초 안쪽이지만, 수십억 개를 대입하려면 너무 오래 걸리게 만든다.
- DB 에 저장되는 모양: `pbkdf2_sha256 $ 1000000 $ 소금(22자) $ 해시(44자)`

## 5. 전체 점검 (11-05 오전)

실제 서버에 대고 정상 동작과 막혀야 하는 경우를 한꺼번에 시험했다.

| 점검 | 결과 |
|---|---|
| 로그인 전 대화 화면 | 로그인 화면으로 (302) ✅ |
| 로그인 전 API (목록 · 채팅 · 삭제) | 401 · 403 으로 막힘 ✅ |
| 보안 토큰(CSRF) 없이 로그인 | 403 ✅ |
| 로그인 API 에 GET | 405 ✅ |
| 가입 검사: 아이디 규칙 · 띄어쓰기 · 6자 미만 · 확인 불일치 · 중복 | 다섯 가지 모두 이유를 알려 주고 막음 ✅ |
| 비밀번호 빈칸 · 틀린 비밀번호 · 없는 아이디 | 같은 안내 ✅ |
| 로그인 → 대화 화면 → 새 대화 → 목록 → 로그아웃 → 다시 막힘 | ✅ |
| 없는 대화 열기 · 빈 질문 | 404 · 400 ✅ |
| 남의 대화 삭제 | 404, 그 대화는 그대로 ✅ |
| DB 저장값 | `pbkdf2_sha256` 해시, 원문 없음 ✅ |
| Django 점검 · 화면 CSS · 콘솔 오류 | 문제 없음 ✅ |

### 찾아서 고친 문제: 응답 시간으로 아이디가 드러남

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 없는 아이디로 로그인 | 486ms | 1189ms |
| 있는 아이디 + 틀린 비밀번호 | 1216ms | 1110ms |

- 안내 문구는 같았지만, 있는 아이디일 때만 해시 계산(100만 번)을 해서 0.7초가 더 걸렸다. 시간만 재도 아이디가 있는지 알 수 있었다.
- 없는 아이디일 때도 미리 만들어 둔 가짜 해시로 같은 계산을 한 번 하게 해서 시간을 맞췄다 (Django 가 권하는 방식).
- 배운 것: 문구를 똑같이 맞춰도 **걸리는 시간**이 정보를 흘릴 수 있다. 화면에 보이는 것만이 아니라 측정해 봐야 보인다.

## 6. dev 병합 전 확인

`dev` 에 ②의 분류기 개선(분류기 노드 · 프롬프트 · 그래프 상태 · `client.py`)이 새로 들어와 있어서, 합치기 전에 확인했다.

| 확인 | 결과 |
|---|---|
| `client.ask()` 를 부르는 방법 · 돌려주는 모양 | 그대로 → 채팅 API 수정 필요 없음 |
| 새로 생긴 것 | 처리 과정에 분류 이유 한 줄, 코드 없이 변환을 요청하면 안내 글로 답함 |
| 겹치는 파일 | 없음 (dev 는 화면 · 뷰 · users 를 건드리지 않음) → 충돌 없이 병합 |
| 실제 그래프로 3가지 | 코드 변환: 5단계가 하나씩 도착, 검사 1회 통과 / 문서 질문: 이제 문서 검색으로 분류됨 / 코드 없이 변환 요청: 안내 글 |
